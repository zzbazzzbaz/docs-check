# test2 — 三方对账

同一批 docx，三个来源各抽一遍「有效格式」，逐字段比对：

| 来源 | 是什么 | 怎么跑 |
|---|---|---|
| `docxfmt/own.py` | 自研：只用 zipfile + lxml，自己按 OOXML 级联合成 | 本地 |
| `docxfmt/foss.py` | aspose-words-foss | 本地 |
| `docxfmt/wps.py` | WPS 本体（headless WPS + pywpsrpc） | 容器内 |

WPS 侧是真值。自研跟它差在哪，就是自研错在哪。

## 跑

```bash
cd test2
uv sync                # 首次
./run.sh               # 全语料：自研 + foss → WPS 容器 → 对账报告
./run.sh corpus/某篇.docx    # 只跑一篇
```

WPS 镜像来自 `../deploy/wps/`（没有会自动构建）。想看 compose 长驻服务那条路径（健康检查 +
`docker exec`）：`./wps_service_check.sh`。

产出都在 `out/`：`<篇名>.own.json`、`.foss.json`、`.wps.json`，对账明细 `compare.json`。

## 语料

`corpus/` 39 篇：

- **29 篇**来自老系统 `2026.6/毕业设计格式审核系统`：28 个规则样张（abstract / acknowledgements /
  appendix / cover / global / main-text / references / table-of-contents）+ 论文初稿 1 篇
- **10 篇真实论文**（来自 `docs/chat/9.25/测试使用数据-论文均为docx`）

真实论文是价值最高的部分：28 个规则样张跑出来是 100%，加入真实论文后立刻暴露了 5 个问题。

## 口径

- **配对**：按「同一文本的第 k 次出现」配对。WPS 把表格行末标记也算段落，按顺序对齐会错位。
- **只比正文**：`story == "main"`。页眉页脚两侧都产出了，但暂不参与比对。
- **文本框不下钻**：自研既定口径，`w:txbxContent` 跳过。
- **容差**：缩进/间距/行距 0.6pt，字号 0.2pt。不同 WPS 版本间存在 0.25pt 级差异，规则比较必须带容差。
- **WPS 未定义值**：超链接/域里的字符，WPS 返回字体 `''`、字号 `9999999`，单独计数不计入不一致。
- **字体名归一**：WPS 报英文名（宋体 → SimSun），`wps.py` 里的 `FONT_ALIAS` 转回中文名；
  比较时再统一小写取第一个字体族。

### 几条容易算错的口径（都是被真实论文暴露出来的）

**字体槽按槽级联，不是按属性叠加。** `w:ascii` 与 `w:asciiTheme` 是同一个槽的两种互斥写法，
近层写了主题引用就要顶掉远层的显式值。反例：`toc 1` 样式写 `asciiTheme=minorHAnsi`，
它继承的 `Normal` 写 `ascii=Times New Roman` —— 结果是主题的 minorHAnsi（等线），不是 Times New Roman。

主题里 `a:ea` 为空时，WPS 回退到同一 scheme 的 `a:latin`（实测口径，非文档所述）。

**字体名归一要在比对层做，两边都归一。** 文档里可能直接写英文名（`SimSun`），WPS 也报英文名，
而自研另一处可能给出中文名；`SimSun` 与 `宋体` 是同一款字。取值层（`own.py` / `wps.py`）只报原始名字，
归一交给 `compare.py` 的 `first_family → canon_font`（`common.py` 的 `FONT_ALIAS`）。

**行距：文档从没写过 `w:spacing` 时，有效值是单倍（`w:line=240 lineRule=auto`），不是"未设置"。**
`own.py` 会把这个默认值补上；否则规则层到处要处理 `None`。

**首行缩进：`firstLineChars > 0` 按「字符数 × 段落第一个 run 的字号」，否则用 `firstLine` 缇值。**
实测 5909 段写过 `firstLineChars` 的段落，`|WPS − 字符×字号|` 平均 0.005pt，
`|WPS − 缓存缇值|` 平均 0.318pt —— 字符口径是对的（TOC 条目里最长见：
缇值 20pt 而 chars=4/字号 12 → WPS 报 48pt）。

**悬挂缩进在 Word 对象模型里就是负的首行缩进。** `w:hanging="440"` → WPS 的 `FirstLineIndent`
报 `-22.0`。所以 `own.py` 的 `ind_first` 是**带符号的有效值**（悬挂为负），
`ind_hanging` 另外保留悬挂的幅值。

**可见文本 `w:t` 有三个坑**（48 条文本类规则全靠它，错了会连锁误报）：

- `w:tab` 有两处含义：`w:r` 里的是制表符（记 `\t`），`w:pPr/w:tabs` 里的是**制表位定义**，不是字符；
- `m:t`（公式文字）**是**可见文本（WPS 的 `Range.Text` 就含它），要收；但公式文字属于 `m:r`，
  所以「整段是公式」的段落没有 `w:r`，字符级属性无从采样 —— 这类段落跳过字符级比对；
- `w:noBreakHyphen` / `w:softHyphen` 要记成真正的字符（`\u2011` / `\u00ad`）。
  Word 用控制符表示它们（`\x1e` / `\x1f`），比对时换算。真实论文里确有此类字符（`TSW‑30`、`E‑R`、`NEO‑6M`）。

**字符级属性按字符采样，口径与字体一致**：西文槽取「第一个含 ASCII 字母数字的 run」，
中文槽取「第一个含中文字的 run」，WPS 侧取同一个字符。所以加粗/斜体/下划线/上下标
比的是**同一个采样点**的属性，不是整段。

## 未决项：`firstLineChars` 与缓存 `firstLine` 不一致时听谁的

6 处，都在 `2206181072_李煜` 一篇。该段直接 pPr 写的是 `ind[firstLine=464 firstLineChars=200]`，
字号 12pt → 字符口径 `2 × 12 = 24.0pt`，缓存缇值口径 `464/20 = 23.2pt`。

- 自研按 `firstLineChars` 语义算 → **24.0**
- WPS 报 **23.2**，而且 **aspose-words-foss 也报 23.2**
- 但同一篇里另 236 段结构相同、缓存 `firstLine=480` 的段落，WPS 报 24.0；
  全语料里 `toc 3` 样式写 `firstLine=400 firstLineChars=400`、字号 12pt 的段落，
  WPS 报 48（按字符重算）而不是缓存值 20

也就是说 **WPS 自己不一致**。全语料做过距离统计（5909 段写了 `firstLineChars`）：
`|WPS − 字符×字号|` 平均 0.005pt，`|WPS − 缓存缇值|` 平均 0.318pt；
其中字符口径更近的 370 段、缇值更近的 7 段、其余 5532 段两者本来就一致。

`w:firstLine` 与 `w:firstLineChars` 是同一个缩进的两种写法，OOXML 没有规定不一致时谁优先。
**要定论必须拿渲染真值**（把 docx 转 PDF 量几何位置），本轮没做。自研暂时保持字符口径。

## WPS 侧的限制

`Range.Text` 遇到**星形平面字符**（U+10000 以上，例如数学斜体 `𝐵` = U+1D435）会坏：
pywpsrpc 按 UTF-16 单位数创建 Python `str`，而真实字符数更少，多出来的位置是未初始化内存，
一读到就 `SystemError: invalid maximum character passed to PyUnicode_New`。

处理方式：取最长可读前缀并标记 `text_truncated`，这类段落不参与比对（`compare.py` 会报数量）。
真实论文里这类段落多得多（44 段，来自公式/特殊符号）。从 `Characters` 逐字救不回来——
`Character.Text` 取不到。

### `w:sdt`（内容控件）首段的 `Characters` 会多一个前导元素

目录在 Word 里常被包成内容控件 `<w:sdt>`。WPS 对这种块的**首段**，
`Range.Characters` 集合里多一个前导元素，`Item(i+1)` 取到的是隔壁字符——整段偏一位
（首字符位置取到幻影，字体回落成 docDefaults）。同一内容控件的第 2 段以后正常。

实测语料里这 3 个目录首段全中：

| 段落 | 应该采的字符 | WPS 实际采到 |
|---|---|---|
| `目  录` | 第 0 位 `目` | 幻影 `None` → 回落默认字体 |
| `第四章 系统设计 \t 20` | 第 11 位 `2` | 第 10 位空格 → 宋体 |
| `6.3 用户端功能测试 \t 52` | 第 4 位 `用` | 第 3 位空格 → Times New Roman |

取值侧的处理（`wps.py` 的 `_sample`）：不盲信 `Item(i+1)`，把返回字符和文本里该位置的字符对一下，
对不上就试相邻下标，都不对再退回原样。这样不依赖「它是内容控件」这个前提，对其它偏移也稳。

## 空段落与段间序列

「其后正好 1 个空段落」那类规则（9 条）要的不是单段属性，是**段与段之间夹了几个空段落**。
所以这块比的是：每段的「是否空」+ 配对相邻两段之间的空段落数。

### 口径（都不显然，逐条实测出来的）

- **WPS 的 `Paragraphs` 每个表格行末多一个空段落**。自研侧用 `row_end` 标出行末，
  比对时按「自研下标 + 之前的行末标记数 = WPS 下标」对齐。
  39 篇的段落数（自研 + 行末标记 == WPS）**全部精确相等**。
- **「空段落」有两种口径，必须分开**：
  - **文本口径**（`text_empty`）：无可见文字 → 与 WPS 可比，用于对账；
  - **规则口径**（`is_empty`）：无文字 + 无图片（含浮动）+ 无公式 → 更严，WPS 表达不了「无浮动图」那半，
    留给规则用。
- **WPS 的 `Range.Text` 里有一堆控制字符，都不是可见文字**：
  `\x01`（内嵌对象占位符）、`\x02`（脚注/批注引用）、`\x13\x14\x15`（域起/分隔/止）、
  `\x05\x0e\x07\x0c\a` 等。不把它们去掉，含内嵌图形的段落（自研是 `(3-1)`、WPS 是 `\x01(3-1)`）
  会因为文本对不上而**整段配对失败**——修掉之前有 93 段是这么丢的，修完剩 0。
- **谁会给「占位字符」**：按 WPS 的 `InlineShape.Type` 分，**不按文字** ——
  **内嵌图片（Type=3）给 `/`**、**OLE 对象（Type=1）给 `\x01`**，两者无交叉；浮动图形不给。
  因为 `\x01` 属控制符会被可见文本去掉、而 `/` 不会，所以
  **文本口径的空段落判定只看 `wp:inline` 图片**（OLE 那段的文本会被清成空，与自研一致）。

## 图片 / 公式对象对账

`own.py` 每段产出对象计数（`objects`），`wps_objects.py`（容器内）取 WPS 真值并**把每个对象归属到段落**，
`objects_compare.py` 对账。覆盖 `TXT-32`~`TXT-36`（公式）与 `TXT-37`~`TXT-42`（图）那批规则的识别前提。

比对字段：每篇的内嵌图形数 / 浮动图形数 / 表格数 / OLE 公式数 / OMML 公式数；
逐段的「本段含内嵌对象 / 浮动对象 / OMML」；以及「图题前一段是图」（`TXT-38` 依赖的顺序数据）。

### 口径（四个坑都是实测撞出来的）

- **`m:oMathPara` 只是 `m:oMath` 的容器**，两个都数会重复（论文初稿数出 53，WPS 说 37）。只数 `m:oMath`。
- **`mc:AlternateContent`**：Word 会同时写 DrawingML（`mc:Choice`）与 VML（`mc:Fallback`）两份，
  是**同一个对象**，`mc:Fallback` 里的要跳过（实测 4 vs 2）。
- **独立 VML 图形（`w:pict`）按定位样式分**：带 `mso-position-*`（或 `position:absolute`、`w10:wrap`）的
  是浮动，WPS 算 `Shape`；否则算 `InlineShape`。
- **`Tables.Count` 只数顶层表格**（嵌套表格不单独计，实测 6 vs 5）。
- 计数对应关系：自研 `wp:inline + pict_inline + w:object` ↔ WPS `InlineShapes`；
  自研 `wp:anchor + pict_float` ↔ WPS `Shapes`；`m:oMath` ↔ `OMaths.Count`；顶层 `w:tbl` ↔ `Tables.Count`。
- 规则里「图」的定义是 `w:drawing`（不含 VML `w:pict`），「公式」是 `w:object` 或 `m:oMath`。
- 「图题在图下方」是可验的：两边各自算「图题段的前一段是不是图」，按图题出现次序配对。
  **局限**：自研的段落是扁平列表（表格段落内联进来），跨表格的块级顺序还判不了。
- 逐段归属用**位置对齐**（WPS 段落 = 自研段落 + 每个 `w:tr` 行末一个占位段），40 篇段落数精确相等；
  实跑 **50547/50547** 逐段对象数一致（子智能体的独立核验脚本）。

## 域与 TOC 跨度对账

规则里「目录条目」的定义是 **`TOC` 域内、样式名 ∈ {toc 1,2,3} 的段落** ——
一半是域（**可对 WPS 验证**），一半是样式名（WPS 取不到，见下）。

`own.py` 的 `fields` 产出每个域的**代码名**（begin/end 按栈配对后取 `w:instrText` 的第一个词）、
**起始/结束段落号**、嵌套深度、是否合成域；每段还挂 `field_codes`（只含真实域）。
`wps_fields.py` 取 WPS 的 `Fields`（`Code.Text` / `Type` / `Code.Start` / `Result.End`）并映射到段落；
`fields_compare.py` 对账。

比对字段：域总数、域代码分布（多重集）、TOC 域跨度、逐段的「本段有域 / 本段域代码」。

### 口径（三条都是实测撞出来的）

- **WPS 的 `doc.Fields` 不等于 `w:fldChar`**：它还会把 `w:object`→`EMBED`、
  正文 `w:hyperlink`→`HYPERLINK`、VML 文本框→`SHAPE` **合成为域**。
  《王雨诺》那篇 `fldChar` 全为 0、WPS 却报 136 个域（121 HYPERLINK + 15 SHAPE），
  就是这个原因。所以 `own.py` 同样记一份并标 `synthetic: True`，**规则判定只用 `synthetic=False` 的**
  （`paragraphs[].field_codes` 就是过滤后的）。
- **TOC 域的「结束段」有两个口径**：`end_para` 是**结束标记所在段**，
  `end_para_content` 是**内容实际结束的段**（结束标记那段若只剩标记、没有别的内容，就是上一段）。
  WPS 的 `Result.End` 对应后者（`论文初稿` 前者 74、后者 73）。对账用 `end_para_content`。
- **按代码名比，不按 `Type` 整数比** —— Type 是版本相关枚举（语料实测 `TOC→13、PAGEREF→37、
  HYPERLINK→88、REF→3、INCLUDEPICTURE→67、SEQ→12、EMBED→58、SHAPE→95、PAGE→33`），
  代码名才是稳定的。域总数与代码分布与 WPS 精确对应（李煜 138 个）。
- **页眉页脚里的域不在 `doc.Fields` 里**（只给正文），页码那批已由页眉页脚对账覆盖。
- 文本框里的域两边都不算（自研不下钻文本框；WPS 的 `doc.Fields` 也不含）。

### 还缺口：样式名没有裁判

`TOC-07`~`TOC-15` 要靠 `toc 1/2/3`、`heading N` 的**样式名**筛段落，而 WPS 的 `para.Style`
是裸 `IDispatch`、取不到名字。自研**已经识别**（`style_id` + `style_name`，15219 段有值），
缺的是独立裁判。可行的替代：用 `foss` 的 `style_name` 当第二裁判（它读同一份 `styles.xml` 但代码独立），
或对 `styles.xml` 做原始抽检。

## 文本框内容对账

自研的**正文口径不下钻文本框**（既定），所以文本框是单独一路：`own_textbox.py` 采 `w:txbxContent`，
`wps_textbox.py` 采 WPS 的 `Shape.TextFrame.TextRange`，`textbox_compare.py` 对账。
覆盖 `GLB-28`（正文 / 表格 / **文本框**都要查自动编号）与文本框内容的核对。

比对字段：框数、锚定段号、文本、段数，以及每段的中文字体 / 西文字体 / 字号 / 对齐 / 编号。

### 口径

- **`mc:AlternateContent` 会写两份**：同一个文本框有 DrawingML（`mc:Choice`）与 VML（`mc:Fallback`）两个
  `w:txbxContent`，要跳过 Fallback（实测 校园便利店 2 vs 1）。
- **`Shape.TextFrame` 可用，但整段 `TextRange.Font` 遇混合格式不可靠**（`Size=9999999`、`Name=None`），
  必须逐段取。
- **组合形状（`Shape.Type == 6`）** 自身的 `TextRange` 报 `0x80000008`，要下钻 `GroupItems`。
- **不能用 `Shape.Type` 认文本框**（DrawingML 矩形报 1），要用 `HasText`；`InlineShapes` 没有 `TextFrame`。
- **锚定段号用 `Shape.Anchor.Start`**（`TextRange.Start/End` 在另一个故事区，不能映射段落）。
- **`GLB-28` 的信号是逐段 `Range.ListFormat.ListType`**（0=无编号，非 0=有；整段 `TextRange.ListFormat`
  是混合值 5，必须逐段取）。实测 `numId=1 → ListType=3`、`numId=0`（取消）→ 0 ✓。

结果：**433/433 = 100.00%**（40 篇；语料里只有 2 篇有文本框，共 16 个框）。

## 块序列与整篇索引（`DocumentIndex`）

规则文档（`9-整体.md`）约定：在语义层之后、规则之前构建一次性只读索引
`modules` / `chapters` / `floats` / `citations` / `toc_entries`。`index.py` 产出自研侧，
`index_check.py` 做验证。

### 这一块**没有 WPS 裁判**

WPS 给不了块类型（`Range.Information` 取不到），也给不了「这段属于哪个模块」的语义分区。
所以验证换成三条（`index_check.py`，40 篇全通过）：

1. **不变量**：块序列恰好铺满全部段落号（不重不漏）、模块区间连续不重叠、边界段落的文本匹配关键文本、
   章按段号有序且在正文区、引用编号唯一且 order 连续、目录条目层级合法；
2. **独立重算**：用另一种走法（只看**顶层段落块**）重算模块边界，与全段扫描的结果比 ——
   不一致就说明边界是从表格内部捞出来的；
3. **跨模块对齐**：段落数、TOC 域跨度等输入取自已由 WPS 验证过的产物。

### 口径

- **块序列**是 `w:p` 与 `w:tbl` 的交错。走表格时要按 `tr/tc` 下钻（`iter_paragraphs` 只看子元素是
  `p/tbl/sdt` 的情况，对表根会数出 0 个）；进 `sdt` 时**段号计数器要接着走，不能重置**。
- **索引宽松收集，规则负责收缩**（`9-整体.md` 的纪律）：`chapters` 收「文本以 第…章 开头」的候选，
  并把 `outline` / `style_name` / `is_heading1` 一并带上，由规则收缩。
  只看文本会把「章节安排」那类行文也收进来（李煜 14 个候选 vs 严格 5 个）。
- **章号要认阿拉伯数字**：论文初稿用的是「第3章」（不是「第三章」）。
- 「目录条目」只按**样式名** `toc 1/2/3` 判，**不按 TOC 域区间**判 —— 目录标题那段往往就是
  TOC 域的 begin 段，按区间排会把它一起排掉。
- 图/表编号重复**只提示不判错**：正文里「图4-1 所示」也匹配图题模式，重号可能是文档歧义，
  要靠规则层（`TXT-38` 的「在图下方」）再收缩。

结果：**7 项不变量 40/40 全通过**；2 篇有图/表重号（提示）。

## 表格边框对账

规则 `TXT-49`（三线表）要判表格边框。`own_borders.py` 采自研侧，`wps_borders.py` 采 WPS 的
`Table.Borders` / `Cell.Borders`，`borders_compare.py` 对账。采样口径两边一致：**前 2 行 × 前 3 列**。

比对字段：表数、行数、列数，以及每个采样单元格的上 / 下 / 左 / 右四边「有没有线」。

### 口径（关键是单元格的继承模型）

- **`Cell.Borders` 不是「直接继承表级同名边」**：那样做 bottom 只有 64.5% 一致。
  正确模型是**按位置映射** —— 单元格自己的 `tcBorders` 优先，否则
  上边：首行取表 `top`、其余取表 `insideH`；下边：末行取表 `bottom`、其余取表 `insideH`；
  左/右：首列取 `left`、末列取 `right`、其余取 `insideV`。
  换成这个口径后**四边全部 100%**（「仅直接」的 95~99% 正好反证必须有继承）。
- **只数顶层表格**（嵌套表格 WPS 不单独计，实测 6 vs 5）。
- **WPS 不认 `tblStylePr` 条件格式**：靠表格样式做三线表（表头下框线用 `firstRow`）会丢线，
  自研认、WPS 不认 → 这类表会对不上。**本语料没踩到**（论文初稿 / 数学论文初稿把三条线直接
  写成了 `tcBorders`）。
- `LineStyle` 只有 0 / 1 / 9999999；宽度就是 `w:sz`（1/8 pt）；`9999999` 是未定义，对账时跳过。
- 合并视图（`gridSpan` / `vMerge`）会让**表级**边界出现建模差异（子智能体独立核验里 31/228 表如此），
  单元格级四边不受影响。

结果：**单元格四边 1179/1179（每一边）= 100.00%**，表数 / 行数 / 列数 100%。

子智能体另做了独立核验：**三线表可判** —— OOXML 真值 210/228 = 92.1% 是纯三线表，
用 WPS 信息判**正判 210/210、误判 1**（要逐单元格读 `Borders.Bottom`，表级 `insideH` 对三线表
恒为未定义）。

## 段落样式名（无 WPS 裁判）

样式名是 `TOC-07/12/13/14/15`、`APP-13`、`REF/ACK/APP-04` 那批规则的前置。
WPS 的 `para.Style` 是裸 `IDispatch`，取不到名字，所以**只能用「两个独立实现读同一份 `styles.xml`」互证**：

- 自研 vs `foss`：在 `foss` 能判的 **5875 段上 100% 一致**；
- `foss` 对**没写 `pStyle`** 的段落不套默认段落样式（它的已知缺陷），这类有 **5596 段**，
  它给不出值 —— 这部分**没有裁判**，如实计数。
- 派生量（规则真正要的）：**目录条目数（`toc N`）40/40**、**标题数（`heading N`）40/40** ——
  因为 `toc N` / `heading N` 段落都直接写了 `pStyle`，正好落在能判的那一侧。

## 页面设置 / 分节 / 页眉页脚对账

`own_pages.py`（自研）与 `wps_pages.py`（WPS，容器内）取同一套东西，`pages_compare.py` 对账。
覆盖 `GLB-15`~`GLB-19`（纸张、页边距）与 `GLB-01`~`GLB-14`（页眉页脚页码）那批规则。

比对字段：节数、页宽/页高、方向、四边页边距、页眉距/页脚距、页码格式、首页不同、奇偶页不同，
以及每个节 × 3 种类型（default/first/even）× 页眉/页脚 的：文本、是否本节自有引用、PAGE 域数、
段落的中文字体/西文字体/字号/对齐。

### 口径

- **分节**：OOXML 里 **body 级 `w:sectPr` 是最后一节**，段落级 `w:pPr/w:sectPr` 结束它所在那节。
  按文档顺序展开后与 WPS 的 `Sections.Item(k)` 一一对应（已用 66 节的论文验证过）。
- **页眉页脚按节继承**：本节没引用该类型，就沿用上一节生效的那个部件。WPS 报的也是**生效后**的内容，
  所以两边都按「生效值」比；另用 `has_reference` 单独比「本节是否自己拥有」。
- **含 `PAGE` 域的页眉页脚，文本不可比**：WPS 报实时页码，自研只能读 XML 里缓存的域结果。
  所以「有没有页码」必须靠数域（WPS `Range.Fields` 里 `Type=33`，自研数 `w:instrText`/`w:fldSimple`），
  不能靠文本 —— 这也是 `GLB-06`/`GLB-07`/`GLB-11`~`GLB-14` 的实现依据。
- **第一节分不出「无引用」与「引用空部件」**：WPS 的 `HeaderFooter.LinkToPrevious` 在第一节恒为假
  （没有上一节），所以「本节自有引用」这一项跳过第一节。
- **`doc.PageSetup` 在多节文档里返回 `9999999`（wdUndefined）**，必须逐节取 `Section.PageSetup`。
  （子智能体实测：66 节的论文里 `doc.PageSetup` 六个边距全是 9999999，逐节取才拿到 10 组正确值。）
- WPS 的 `Headers.Count`/`Footers.Count` **恒为 3**（与是否启用无关）；空页眉/页脚是 `1` 个空段落、
  `Range.Text` 为 `"\r"` 而不是空串。
- **继承来的页眉页脚，WPS 报的字符属性是未定义的**：`Font.NameFarEast` 返回空串、
  `Range.Fields` 返回 0（它只数本节自己的对象）。所以「页眉页脚中文字体」在 WPS 给空串时跳过，
  「PAGE 域数」只在本节自有时比 —— 都按主对账的同一口径处理。
- **文本框不下钻**：页眉页脚里图形内的段落（`txbxContent`）不计。WPS 的 `Range` 也不含图形内文字，
  两边口径天然一致；`wps.py` 的 `Fields` 同样不数图形内的 PAGE 域。

## 已知差异（自研无错，是 WPS/库的怪癖）

- WPS 的 `Paragraphs` 比自研多表格行末标记（论文初稿：201 vs 192），所以配对按文本、不按序号。
- WPS 对超链接/域里的字符返回未定义：字体 `''`、字号与 `Font.Underline` 返回 `9999999`
  （`wdUndefined`），不可比，单独计数。
- foss 的段落没写 `pStyle` 时不套默认段落样式；页眉页脚忽略 run 显式写的 `eastAsia`；
  所以它的中文字体槽经常回退到主题字体（Calibri 之类）。
